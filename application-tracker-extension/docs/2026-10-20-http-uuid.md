# 2026-10-20 普通 HTTP 扫描兼容修复

用户刷新扩展后，在普通 HTTP 申请页面仍得到 PAGE_SCAN_FAILED，要求与 Claude 讨论。前轮访问恢复只改善了分类与入口，没有解决此页面的扫描根因。

## 证据和讨论

本机 Chrome 155.0.8059.85、一次性配置和真实 MV3 注入原始 fc8530d 源码：

| 来源 | isolated world 安全上下文 | randomUUID | 原始扫描 |
|---|---|---|---|
| http://bank-fixture.test | false | undefined | 无有效结果，session 报 PAGE_SCAN_FAILED |
| http://127.0.0.1:8765 | true | function | 识别 3 题 |
| https://secure-fixture.test | true | function | 识别 3 题 |

在普通 HTTP 的直接 UUID 调用实际得到 TypeError: crypto.randomUUID is not a function。页面在浏览器中保持真实非 localhost HTTP 身份，使用 route.fulfill 提供虚构 HTML；未降低安全设置或把 HTTP 当成安全上下文。Chrome 对注入 async 函数的该异常没有返回可用结果，也没有 reject，所以前轮无法从调用端取得原异常。

Claude 报告在其 Linux Chromium 141 / MV3 / 虚构域名映射环境也得到一致现象。该报告是协作证据，本轮采用方案仍由 Codex 根据 Windows 本机实测独立判断。双方同意只修改注入网页的 pageBridge，不改扩展页面与后台原生 UUID；后者本身处于安全上下文。

Claude 最初建议对整个函数统一 try/catch。Codex 先限定为 scan；Claude 随后提出初始化发生于事务之前、changes 也会调用描述器等具体反例。本机新增检查支持这些反例，因此最终采用所有 action 共用的初始化诊断，以及 scan/changes 的只读收集和描述守卫，保留 fill/undo 事务、可信人工修改和失败撤销内部异常语义。bridge 与 session 两端均限制阶段和异常类型白名单，任意 error.name 也不能直接输出。新增控件几何故障按实际发生点报告 discover，已有字段描述故障报告 describe，不人为混成一个阶段。

## 实现

- pageBridge 内定义自包含 randomId helper：原生 randomUUID 可用时沿用；否则 getRandomValues 读取 16 字节并设置 UUID v4 version/variant，维持原有 token 与 scanId 语义。
- 扫描诊断仅含 status、固定 code、stage、白名单 errorName、secureContext；不包含 message、stack、URL、选择器、字段值、资料或凭据。
- session 区分 BRIDGE_NO_RESULT 和 BRIDGE_EXCEPTION，并把固定中文阶段/异常类别/环境展示给用户。异常结果不能成为空的成功预览。
- 忙碌与过期只读请求显式返回 BRIDGE_BUSY / SNAPSHOT_STALE；轮询遇忙保留计划等待下次检查，遇真正异常展示安全诊断并停用计划。ping 与 changes 先检查空响应和结构化失败，不借助 TypeError 或令牌不匹配把故障误报成跳转。
- 新增独立 test:http，不依赖未公开的网页 HTML；测试临时 manifest 只授权虚构来源，生产 manifest 和权限不变。

参考：[randomUUID 的安全上下文要求](https://developer.mozilla.org/en-US/docs/Web/API/Crypto/randomUUID)、[getRandomValues 可用于非安全上下文](https://developer.mozilla.org/en-US/docs/Web/API/Crypto/getRandomValues)。

## 复现和验证边界

最终适用检查 569 项通过：358 单元、129 浏览器（35 原生、15 岗位、46 组件、14 选择组、5 日期格式、14 上下文）、49 助手 UI、15 原有 MV3、7 截图浏览器、11 HTTP 上下文 MV3。本轮未重复数据 UI、性能/慢 CPU 和六时区套件，先前记录不计入本轮。

并发回归有两次 MV3 在自我介绍填写/撤销核验时未达到预期，一次组件页导航超过原有 5 秒；另一次浏览器重跑被随机分配的 6669 端口触发 Chrome ERR_UNSAFE_PORT，尚未进入表单验证。失败日志均保留；没有放宽断言、生产等待时间或浏览器安全设置，改为串行复测。核验波动原因未确认，不能用重跑成功宣称从无波动。

交付位于 docs/delivery/2026-10-20-http/，含最终日志、实验日志、可应用补丁、原始字节哈希与当前源码包。补丁相对本轮前本地备份；公开同步另有 SOURCE_MANIFEST，继续排除真实浏览器数据、凭据、网页 HTML、日志及私有协作记录。

原始失败和临时副本候选成功均已实测保存，然后才修改主源码。新增用例覆盖三种来源的扫描、UUID 格式、token 稳定/scanId 更新、填写、撤销、真实选项读取、变化检查、旧快照拒绝和人工改动保护；另有真实侧栏 HTTP 预览、初始化故障跨 action/client 传播、changes 阶段诊断、任意异常名称清理与预期忙碌/旧快照结果。扩展页面生成的 ID 仍使用原生 API。

第三轮 Claude 没有发现新的关键反例，并接受新增几何错误归 discover 的纠正。它建议对核验波动做单独 4 倍 CPU 小实验；本机普通 HTTP、真实 MV3、单个虚构自我介绍 textarea 连续 5 次填写/撤销均 verified，实际值均清空。这个有限的阴性结果不能解释并发失败原因；实验不计入 569 项正式套件，也不等同于银行或完整侧栏流程。

银行现场仍未取得隔离上下文读数或完成填写验收；本轮证明普通 HTTP 兼容性缺陷并修复，不代表该网站所有控件已适配。原始探针保存在本地 test-artifacts，协作私有 URL 与对话记录位于工作区 work/，不加入公开源码。
